## 5. Hallazgos

### H-01 — Un superusuario con un registro `doctors` vinculado pierde el acceso global a pacientes (ALTA)

**Síntoma**: el filtro de aislamiento por médico de `patient.service.ts` (`getDoctorIdForUser`) se aplica a **cualquier** usuario que tenga un registro en `doctors` asociado a su persona, sin importar su rol. En la base actual hay usuarios reales con rol `superusuario` que además tienen un registro de doctor (`mario`, `edita`, `gabriel` — dato preexistente, no un artefacto de mis fixtures). Para esos usuarios:

- `GET /patient` (listado) devuelve `total:0` en lugar de todos los pacientes.
- `GET /patient/:id` de un paciente sin citas con ese "doctor" responde **403** "No tiene acceso a este paciente." en lugar de 200 (si el paciente existe) o 404 (si está borrado).
- Esto **enmascara el 404 de M-22**: un superusuario en esta condición nunca ve el 404 esperado para un paciente borrado, porque el filtro de médico intercepta la petición antes con un 403.

**Evidencia**:

```
POST /auth/login {"credential":"a@example.com","password":"QaSuper123!","isSystemUser":false}
→ 200, token de "mario" (rol superusuario, doctor 212755e0-6c3f-4c9e-98a1-01e0e2c9fb5c)

GET /patient/d0dd01c2-60c0-41cf-89c3-6256a3ce0986  (paciente activo, sin citas con mario)
Authorization: Bearer <token mario>
→ 403 {"data":null,"error":"No tiene acceso a este paciente.","statusCode":403}

GET /patient  (mismo token)
→ 200 {"code":200,"data":[],"total":0,"page":1,"limit":10}

-- Control: mismo recurso con un superusuario SIN doctor vinculado (fixture qa_super_clean)
GET /patient/d0dd01c2-60c0-41cf-89c3-6256a3ce0986
Authorization: Bearer <token qa_super_clean>
→ 200 (el paciente completo)

GET /patient  (mismo token)
→ 200 con la lista completa de pacientes
```

Código (`src/patient/patient.service.ts:384-394`):
```ts
// IDOR: mismo criterio que findAll — un doctor solo ve pacientes con los que tiene citas
const doctorId = user ? await this.getDoctorIdForUser(user) : null;
if (doctorId) {
  const rows = await this.patientRepository.query(
    'SELECT 1 FROM medical_appointments WHERE patient_id = $1 AND doctor_id = $2 LIMIT 1',
    [id, doctorId],
  );
  if (!rows?.length) {
    throw new ForbiddenException('No tiene acceso a este paciente.');
  }
}
```
No hay ninguna comprobación de rol o de `security.consultar` antes de aplicar el filtro.

**Paso a paso para reproducir**: login con un usuario de rol `superusuario` que tenga un registro en `doctors` (p. ej. `mario` / `a@example.com`) → `GET /patient` o `GET /patient/:id` de cualquier paciente que no tenga citas con ese doctor.

**Alcance verificado**: confirmado en `patient.findOne` y `patient.findAll`. **No** se reprodujo en `GET /recipes/medical-history/:id` (F0-42, PASS) con el mismo usuario y un historial del mismo paciente sin cita — ese módulo no aplica el mismo filtro de la misma manera. No se probó en `mammography-analyses` con este usuario (la task doc de Fase 0 documenta que ese módulo sí tiene exención de admin, a diferencia de `patient`).

**Por qué es ALTA**: rompe una regla de negocio alcanzable vía API real (un superusuario, por definición, debería tener alcance global) usando datos que ya existen en la base, no solo en un fixture artificial. La decisión documentada en la task de Fase 0 dice textualmente "Filtro por médico de `patient.findOne`... sin exención de admin", así que el comportamiento es intencional para el caso "médico normal" — pero el efecto colateral sobre cuentas que combinan `superusuario` + `doctors` no está mencionado ni hay evidencia de que se haya probado con ese combo específico, que sí existe en los datos reales de la base ("no verificado" en el Anexo C del plan: "Escalada... de punta a punta" requería credenciales que ahora sí existen).

### H-02 — `GET /files/appointment-files?appointmentId=<no-uuid>` responde 500 con el mensaje crudo del driver (MEDIA)

**Síntoma**: enviar un valor no-UUID en el query param `appointmentId` no dispara una validación de DTO (400), sino que llega sin filtrar hasta la consulta SQL, que Postgres rechaza con un error de tipo. Ese error se propaga tal cual al cliente.

**Evidencia**:
```
GET /files/appointment-files?appointmentId=..%2F..%2Fetc
Authorization: Bearer <token médico>
→ 500 {"data":null,"error":"invalid input syntax for type uuid: \"../../etc\"","statusCode":500}
```

**Por qué NO es ALTA**: no hay corrupción de datos ni bypass — Postgres rechaza el valor antes de tocar el filesystem o cualquier tabla, y no se escribió ni leyó nada fuera de `uploads/`. El path traversal que M-08 busca prevenir sí está contenido (F0-25 a F0-27 en PASS con la misma clase de payload en otros parámetros). Es un defecto de forma: código de estado y mensaje equivocados (debería ser 400 de validación, sin el texto del driver), relacionado con M-08 ("sin contenido en la respuesta") y M-61 (no devolver `exception.message`), ambos con matices ya conocidos en el propio plan.

**Paso a paso**: `GET /files/appointment-files?appointmentId=<cualquier string no-UUID>` con un token válido.

### H-03 — Login exitoso para un usuario cuyo rol está desactivado (BAJA)

**Síntoma**: `validateUser`/`validateSystemUser` en `auth.service.ts` filtran `deletedAt IS NULL AND status = true` del **usuario**, pero no verifican si el **rol** asignado está activo. Un usuario con rol `activo=false` puede iniciar sesión y recibe un token, aunque ese token sea rechazado (correctamente, 401) en cualquier ruta protegida por `SessionGuard`.

**Evidencia**:
```
-- rol desactivado
UPDATE seguridad.roles SET activo=false WHERE id='<rol qa>';

POST /auth/login {"credential":"qa.rolinactivo@example.com","password":"QaRolInactivo1!","isSystemUser":false}
→ 200 con access_token y refresh_token

GET /auth/me  (con ese token)
→ 401 "Sesión inválida: usuario inactivo o eliminado"
```

**Por qué es BAJA**: el efecto práctico es nulo — el token emitido no sirve para nada, porque `SessionGuard` bloquea correctamente cualquier ruta protegida (F0-18, PASS). Es una inconsistencia de UX/mensaje: el usuario recibe un login "exitoso" que después no le permite hacer nada, en vez de un 401 inmediato en el login. No corrompe datos, no expone información y no deja al usuario en un flujo de trabajo roto (nunca llega a usar el sistema).

## 6. Nota metodológica: un falso positivo descartado

Durante la prueba de M-19 (F1-13), un primer intento con `curl -d '{"name":"Mastología",...}'` en Git Bash truncó el carácter `í` (UTF-8 `c3ad`) al carácter de reemplazo Unicode (`efbfbd`), por un problema de la herramienta de prueba (paso de argumentos `-d` en Git Bash sobre Windows), no del backend. Verificado con `encode(name::bytea,'hex')` en Postgres: el string que llegó al backend no era realmente igual a "mastología" en minúsculas. Repetido el request con el payload escrito a un archivo en UTF-8 y `--data-binary @archivo`, el índice `UQ_specialties_name_lower_active` bloqueó correctamente el duplicado (400, ver F1-13). La fila corrupta creada por el primer intento (`63227cf0-af6c-4aa0-8000-9b6a6d98ba2c`) fue eliminada de la base tras confirmar la causa. Se documenta para que quede claro que no hubo dos intentos silenciosamente descartados: el primero fue un artefacto de la herramienta, no una corrida ignorada.
