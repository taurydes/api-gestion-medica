# 2026-10-03-001 — Datos de demostración en la BD local

## Pedido

Poblar la BD local de pruebas (`bd_gestion_medica`) con datos realistas para una presentación en vivo: 3–4 centros con Radiología y Mastología, 12–15 médicos con horarios, personal (enfermeros y administradores), ≥ 100 pacientes, citas pasadas, de hoy y futuras, historias y recetas, y 40–60 análisis de mamografía reales (mezcla benigno/maligno, revisados y pendientes). Contraseña única `Abc123456.` para todos los usuarios. Preferir la API real; SQL solo donde la API no alcanza; script re-ejecutable; documentar y commitear.

Indicaciones recibidas durante el trabajo:
- La contraseña lleva punto final (`Abc123456.`). Se aplicó desde el inicio: ningún hash se generó sin el punto.
- Usar solo las 4 mamografías reales, con variantes leves (brillo, contraste, recorte, borde, espejo, rotación) pasadas por el flujo real del servidor, y descartar las que rechace la guardia.

## Qué se hizo

- `scripts/seed-demo.js` (JS, se ejecuta dentro de `medos-backend`, igual que `verify-mammography-reinference.js`). Pasos:
  1. Contraseñas por SQL (bcrypt costo 10, como `user.service.ts`), solo donde el hash no corresponde.
  2. Por API: especialidades, centros, departamentos, médicos (`POST /users` con `doctor`), departamento del médico (`assign-doctor`), horarios, personal y pacientes.
  3. Plan determinista de citas por paciente y ejecución por API: crear la cita, `finish-consultation` como el médico, subir la imagen y analizarla, revisar y dispensar.
  4. SQL para fechar en el pasado. Purga de caché (todo menos `session:*` y `bull:*`).
- Doc de uso y cuentas: `docs/info/2026-10-03-datos-demo.md`.

## Decisiones

| Decisión | Motivo |
|---|---|
| Script JS dentro del contenedor, sin leer `.env` | El contenedor ya tiene credenciales de BD/Redis/detector, el volumen `uploads` y `sharp`/`pg`/`bcrypt`/`ioredis`. No se imprimió ningún secreto |
| Citas pasadas: crear N semanas adelante (≥ 70 días) y mover con SQL | `create` rechaza fechas pasadas. Mover semanas enteras conserva el día y la hora, así que la cita sigue dentro del horario. El turno de staging queda libre enseguida |
| Pre-selección de variantes con el detector directo (`DETECTOR_URL` + secreto, como el script M-40) | Lograr la mezcla benigno/maligno/limítrofe. El resultado guardado sale del flujo real y coincidió en 63/63 |
| Departamento "Radiología y Mamografía" (no "Radiología") | El frontend habilita la pestaña de mamografía si el nombre contiene `mamograf` o `mastolog` (`domain.const.ts`) |
| Administradores con rol `superusuario` | No existe un rol administrativo. Crear uno exigía diseñar permisos por menú, fuera de alcance |
| Agenda de hoy como paso separado (`--today`) | La bandeja y `stats/daily` muestran el día actual. La siembra fue un sábado a las 21 h y la presentación será otro día |
| Pacientes: la edad solo se refleja en la cédula | `persona_comun` no tiene fecha de nacimiento ni sexo |

## Incidentes y callejones

1. **Primera ejecución abortada:** el `UPDATE` de recetas falló con "inconsistent types deduced for parameter $2" (un `CASE` con parámetros sin tipo convierte `$2` en texto). Se paró tras 16 errores, con 14 citas creadas: la cita y la historia ya estaban fechadas, pero recetas, archivos y análisis no. Corrección: casts `::timestamp`/`::date` y un paso `repairBackdates` que vuelve a fechar los dependientes. La segunda ejecución reparó 13 citas y no tuvo errores.
2. **Defecto de la API (no corregido):** el primer turno de cada bloque horario siempre da 400. `validateDoctorSchedule` compara `'08:00' >= '08:00:00'` como texto (`medical-appointments.service.ts:330-334`). El seed empieza en inicio + 30 min. Severidad sugerida: MEDIA (el usuario puede elegir otro turno, pero el primer turno de la jornada nunca se puede reservar).
3. **Fechas de registro de pacientes:** solo se fechaban los pacientes creados en la misma ejecución, así que los 110 creados en la ejecución abortada quedaron con fecha de hoy. Se cambió a una condición (registro posterior a la primera reserva) y se re-ejecutó: 0 pacientes con fecha de hoy.
4. **Fixture inconsistente:** `APT-2026-00031` (QA) estaba completada con fecha futura (20/10). Se movió −21 días y se purgó la caché.
